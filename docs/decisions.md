## Context for the main decisions

### D-03 Cells
- **Why:** one namespace and database per tenant is too much to operate with many small tenants. A single shared pool can't offer dedicated isolation to the regulated customers we want to win. Cells give both, and the same unit later becomes the customer-hosted deployment.
- **Consequence:** tenant ID goes in every workflow ID, row, index partition, and log line from day one. Routing from a tenant to its cell happens at the ingress gateway.

### D-07 Agent-scoped permissions
- **Decision:** the agent has its own access. Whether the members of a channel the agent is deployed to may see or change what the agent can reach is the creator's responsibility.
- **Why:** this matches how teams think about a shared bot ("the IT helpdesk can see the IT space"), behaves the same for everyone who asks, and makes retrieval simpler and faster.
- **Alternatives considered:** acting on behalf of each user (agents behave differently for each person, and every user must connect every account); "channel-safe" knowledge only (too restrictive for team agents).
- **Risks and the guardrails that come with this decision:**
  - *A creator over-shares:* the admin approves publishing and any wider grants, and sees each grant's live title and parent, a warning when the creator's label and the live title don't contain one another as whole words once normalised, and a diff against the published version; the creator confirms an explicit audience summary when deploying. Where the Notion picker is configured, a new grant must also be picked from the creator's own Notion account, so it cannot exceed what they can see. Without the picker the admin's approval is the only check.
  - *The audience changes after deploy:* a Slack Connect share of the channel is watched and pauses the agent in that channel until the creator confirms again. Who is added to a channel is the admins' responsibility and pauses nothing.
  - *The creator leaves:* target, not built: grants re-checked every night against the creator's access and suspended if it no longer holds, with the owner and the admin notified.
  - *Questions about one person's own records:* see D-17.

### D-13 Notion as the first write action
- **Why Notion works:** many teams already run request trackers as Notion databases. Notion's integration access model (only pages explicitly shared with the integration) maps directly onto agent grants, and Notion is also a knowledge source, so one connector covers both.
- **What it costs us:** Notion has no native idempotency key, so we add a hidden request-ID property that makes a write findable, and Postgres decides which attempt writes (a lease per idempotency key); the lookup before creating is a check, not the guard. "Done" depends on each database's own status property, so creators map it when granting a database. Notion's low API rate limits mean we need per-tenant queuing. Details in [architecture.md §7](architecture.md).
- **Positioning effect:** we no longer start head to head with IT-ticketing products (Moveworks, ServiceNow). The first demo becomes "requests to any team tracked in Notion", which is broader but less of a ready-made helpdesk story. Jira and ServiceNow follow in v2.

### D-17 Requester-scoped data
- **Why:** an agent-level credential can read everyone's records, and the LLM can't be trusted to filter by person. The runtime pins the person field instead and removes it from what the LLM sees.
- **Alternative kept as an exception:** the requester's own account (OAuth), for systems whose API can't filter by person. That account can reach beyond the agent's grants, so those answers go only to a DM.
- **Where answers go:** in the conversation where the question was asked. Everyone the agent serves may already see what it can reach (D-07), so a private reply would add nothing. Rejected: always answering requester-scoped questions privately.

### D-10 Separate task workflows
- **Why:** work outlives the conversation. Keeping tasks separate gives each one its own lifecycle, its own audit trail, and an ID that approvals and webhooks can target. It also keeps conversation workflows short.

### D-11 Approval by default
- **Why:** it's the main defense against prompt injection and model mistakes. It doesn't depend on the model behaving correctly.

### D-15 Connector manifests
- **Why:** with MCP and OpenAPI, *calling* a tool needs no connector-specific code. What needs per-system work is what makes a write safe and trackable: how to avoid duplicates, who it's attributed to, how to know when it's done. Putting that in a manifest makes most new connectors a configuration and testing job instead of an integration build.
- **Consequence:** certified write actions are still added one at a time, because each needs testing against a real instance. Custom connectors never retry writes automatically unless they declare how to avoid duplicates.

### D-16 Connector self-repair
- **Why:** custom connectors are untested when they're added. Catching and fixing their failures quickly is what makes "bring any MCP server" credible.
- **Why Temporal:** the fix process includes waits that can last days (human approval, watching a canary). Using the failure signature as the workflow ID groups many identical failures into one fix.
- **Limits:** only code we own gets fixed; most failures (logins, permissions, outages) are routed elsewhere, not to the coding agent. The agent can't change safety fields, never deploys, and runs in a separate cell with no production credentials. Details in [design/self-repair.md](design/self-repair.md).
- **Rollout:** detection and the circuit breaker first (v2), human-approved fixes next (v3), automatic deploy only for low-risk read-tool fixes later.

### D-20 Tenants in Postgres
- **Decision:** after a one-time import of the YAML file, the `tenants` table is the source of truth for the Slack workspace, the enabled flag, the default agent, channel routing, admins, the Notion workspace and the names of the secret variables. A secret value is never stored. The gateway and the console re-read the table every 15 seconds, the worker every 5, so adding, changing or disabling a tenant needs no restart. An empty table stops a process with a message naming the import.
- **Amended by D-34:** an empty table (or one where every tenant is disabled) no longer stops a process; it logs once and serves none until a tenant is installed or imported. An inconsistent table still stops start-up.
- **Amended by D-36:** tenant settings have a console page: an admin sets the default agent and channel routing, connects Notion and manages the webhook token at `/ui/<tenant>/settings`.
- **Why:** several tenants share one deployment, and a settings change should not need a deploy. Row-level security hides other tenants' rows; the two reads that cross tenants go through narrow `SECURITY DEFINER` functions.
- **Consequence:** editing the YAML afterwards changes nothing. There is no console page for tenant settings yet.

### D-21 Budgets and their stop
- **Decision:** an admin sets a monthly dollar budget for the tenant and for each agent; at or over it the agent answers with a fixed text and calls no model. The tenant budget also stops indexing's embedding calls. Spend that cannot be measured is not zero: a budgeted scope with an unpriced row this month, or a call whose usage row could not be saved, is stopped until the rows are priced or the cache window passes.
- **Why:** a limit that lets unmetered spend through is not a limit. Overspend is bounded, not zero: the other processes' spend in one cache window, plus the calls in flight, plus one call's cost.
- **Consequence:** the worker refuses to start with no price for its chat or embedding model, and prices are matched by name, alias or dated prefix. Deviation: a dropped usage row marks the scope unmetered only in that worker process for one window.

### D-22 Kill switches, and what "agent off" means
- **Decision:** an admin turns an agent, every agent, a connector or all writes off, and on again; each applies on the next step, with no cache. Turning an agent off stops everything it does: new model calls, read tools already dispatched, follow-up polling (the watch ends), its offer to a front door as a specialist, and **a write the requester already approved that has not run**. The card says the agent was turned off by an admin and that nothing was changed, and the task ends without a follow-up watch. A connector that is off makes polling fail retryably, so the task keeps watching.
- **Why:** an admin who turns an agent off during an incident expects nothing more to happen.
- **Consequence:** one gate in front of every activity that acts for an agent applies the agent, writes and connector switches by effect (model, read, write, poll). Only an admin changes a switch. The host operator can use the same switches from the command line, audited as `operator:<OS login>`.

### D-23 A pause or a lost audience stops pending approval cards
- **Decision:** a channel pause, or the requester leaving the agent's audience, stops cards that are already pending. The task re-checks both immediately before the write, refuses with a fixed line on the card ("<agent name> can no longer act for you here; nothing was changed.") and ends; the requester can ask again once the agent is available to them. A check that cannot be completed stops the write too.
- **Why:** a card shown before a pause or a membership change should not outlive it.
- **Consequence:** the task workflow has a pre-write check, behind a workflow version marker so histories recorded before it replay unchanged.

### D-24 Audience watch is limited to shared channels
- **Decision:** an agent is paused in a channel when the channel is shared with another organisation (Slack Connect). A person joining a channel, guest or not, pauses nothing: who is added to a channel is the admins' responsibility, and a guest or outside person who asks the agent is still refused by the audience check.
- **Why:** a share is a fact the event itself carries, so it needs no Slack lookup and has no "could not check" case. Joins are frequent and ambiguous.
- **Status:** built and verified with fakes only; not yet run against a real Slack Connect channel.
- **Resuming:** the agent's creator or an admin confirms a fresh count of the people in the channel, as at publish.

### D-25 Qwen and local embeddings
- **Decision:** the worker can use Qwen (an OpenAI-compatible endpoint) instead of Claude, chosen once at start, and embeddings come from any OpenAI-compatible endpoint, such as a local Ollama model (`bge-m3`). The vector size is fixed by the index column at 1024, so every embedding model must produce it.
- **Why:** testing and development without paying a hosted provider; chat history is stored in one format whichever provider is used.
- **Consequence:** the default Claude model is still the production path (Q-1). Each page records its embedding model, so changing the model re-embeds everything and searches compare only chunks of the model in use.

### D-26 Content stays out of Temporal history
- **Decision:** what people write, what the model replies, each tool call's input and a task's draft live in Postgres under IDs, and Temporal carries the IDs. Deleting a thread's rows deletes what was said in it. The gateway stores a Slack event and answers at once; a relay loop signals the workflow.
- **Deviation 1:** a conversation or task that was running when this change was deployed keeps carrying content in its history until it ends, because histories recorded before the change must still replay. A message signalled by an older gateway has its text inline and is run the way it was; every message after the deploy is content-free, also in a thread that began before it. A task started before keeps its payload in its history until it finishes.
- **Deviation 2:** two small strings can still reach history: the field names a model chose in an invalid tool input, which are told back to it as the reason the call did not run, and a failure reason from an activity (fixed texts from the connector). Neither is what a person wrote or a document held.

### D-27 Payload keys are local versioned files (amends D-12)
- **Decision:** each tenant's Temporal payloads are encrypted with AES-256-GCM under a key kept as a local file (`<tenant>.key`, then `<tenant>.vN.key` after a rotation), owner-only and outside the repo. The key ID `<tenant>/vN` travels with the payload and the workflow ID is the associated data. `python -m agentos.tenant_keys rotate` adds a version; old versions stay so older histories read. A payload with no encrypted tag is refused unless `AGENTOS_ALLOW_PLAINTEXT_PAYLOADS` is set.
- **Why:** it keeps tenants' payloads apart and makes a key swap possible before a cloud key service is chosen. The key store is the one seam where a KMS replaces local files.
- **Known limit:** the `workflow.patched` marker records are written by the Temporal SDK core outside the codec and carry only patch IDs. Not built: KMS and crypto-shredding.

### D-28 MCP and the connector tiers are deferred, not decided against
- **Decision:** the runtime calls Notion through its own connector, behind a manifest that holds each tool's risk class, idempotency method, requester scoping and input schema. There is no MCP client, no OpenAPI adapter, and no certified/custom tiers. This amends D-08 and D-15: the contract stays the goal and is reopened when a second connector is built, since a connector's write safety depends on the system, not on the transport.
- **Why:** one connector does not need a protocol layer, and certified write actions are tested one at a time anyway.
- **Consequence:** architecture §7 keeps the design under a "Target" label.

### D-29 Approving is approving a content
- **Decision:** submit stores the SHA-256 of the definition the version was submitted with. A publish names the hash the approver was shown and is refused if the version carries another, which a withdraw, an edit and a resubmit under the same number would produce. The `agent_publish` event records the reviewed hash. The API refuses a publish with no hash.
- **Why:** an admin's approval is the control that compensates for what the platform cannot yet check about a grant, so it must bind to what was read.
- **Consequence:** a pending version shown before the hash existed has to be reopened before it is published.

### D-30 A creator reads only the agents they created
- **Decision:** a creator lists and reads only the agents they created: definitions, versions, usage, budgets and switches follow one rule, enforced in `ControlPlane`, which the console and the API both call. An agent that belongs to someone else answers "not found", as an agent that does not exist does. Admins read every agent.
- **Why:** a definition holds the system prompt and the access an agent was granted. Before this, usage, budgets and switches were limited to a creator's own agents but definitions were not, so the rule depended on which page asked.
- **Consequence:** the caller's role and owned agents are resolved once per request into a `Principal` that plane calls accept, so a page makes one role lookup instead of one per call.

### D-31 How long a task can live
- **Decision:** an agent definition may ask for an approval window of at most 168 hours (default 72) and a follow-up watch of at most 60 days (default 30). Retention for conversation messages, tool outputs and idempotency records is never shorter than the longest a task can live: 168 hours rounded up to 7 days, plus 60, plus 1, is 68 days. Setting a lower value is refused; the nightly job raises a lower stored one.
- **Why:** nothing a live approval or follow-up still needs may be purged under it.
- **Consequence:** audit and usage rows, external writes, task links and agent definitions are exempt from retention.

### D-32 Keys from host variables, the webhook token in the database (amends D-27)
- **Decision:** a process reads its payload keys either from the local key files (the default, `AGENTOS_KEY_SOURCE=files`) or from host variables named `AGENTOS_PAYLOAD_KEY_<TENANT>_V<n>` (`AGENTOS_KEY_SOURCE=env`): base64 of 32 bytes, `<TENANT>` the tenant ID upper-cased with `-` turned to `_`. Every process chooses through one factory (`agentos.crypto_keys.build_key_store`), so the worker, the gateway and the Temporal client agree. `python -m agentos.tenant_keys value` prints a new key value once, to paste into the host's variables; it never reads or prints an existing key. The Notion webhook verification token is stored encrypted per tenant in the database (the codec's AES-256-GCM cipher, the tenant ID as associated data): the handshake stores it pending and cannot replace a pending or active token; a host command (`python -m agentos.notion_webhook show|confirm|clear`) prints it once, confirms it, or removes it, each audited as the operator. Only a confirmed token accepts events. The tenant's environment variable stays as a local override: while it is set, events use it and the handshake is refused.
- **Why:** a hosted deployment (Railway) has no operator laptop to hold owner-only files; service variables are the hosted equivalent of "exported in the terminal", and the database is already the tenant-scoped, backed-up store. The token no longer needs a gateway volume, nor a restart to export it.
- **Consequence:** rotation on a variable host adds `_V2`, redeploys, and keeps `_V1`; moving a tenant from a key file to a variable is the operator copying the file's content themselves. Two variables claiming one tenant's key version are refused at start-up. Decided by the maintainer 2026-11-19.

### D-33 Tenant payload keys in the database, wrapped by a master key (amends D-32)
- **Decision:** a process may read payload keys from the database (`AGENTOS_KEY_SOURCE=db`): each tenant's key is generated by the app and stored in `tenant_payload_keys`, wrapped with AES-256-GCM under a master key from `AGENTOS_MASTER_KEY_V<n>` host variables (base64 of 32 bytes), with the key ID (`<tenant>/v<n>`) as associated data. New keys use the highest master version; older masters stay while keys wrapped under them are kept. One factory (`agentos.crypto_keys.build_key_store`) still chooses for every process; the database store serves unwrapped keys from memory, loaded at start-up and every few seconds, and a key miss triggers one re-read before refusing, so a tenant installed seconds ago is served without a restart and a missing key stays a retryable workflow-task failure, never a terminal one. `tenant_keys create` and `rotate` write to the database in this mode, audited as `payload_key`; `master-value` prints one new master value once. The app role reads every row of this one table (the codec decrypts for whichever tenant a payload belongs to) and inserts only within its own tenant; stored key versions are never updated or deleted.
- **Why:** Add to Slack must create a working tenant with no manual step: with `env`, every tenant key is a variable a person adds and then redeploys. One master variable set once plus app-generated tenant keys is seamless (nothing per customer) and scalable (any number of tenants). A cloud key service may hold the master key later.
- **Consequence:** the master key never enters the database; a database dump holds only wrapped keys, and a wrapped key copied to another tenant's row does not unwrap. Losing every master version makes every tenant key unreadable, so old master versions are kept like old key versions. The cross-tenant read is confined to this one table; every other table keeps tenant isolation. Two known limits: while a tenant's key is missing, the Temporal SDK cannot encrypt the workflow-task failure either and writes its message in plaintext (it names only the tenant and key version); and each process re-reads every key row every few seconds, a cost that grows with the number of tenants and moves to a watermark or a change notification when it matters. Decided by the maintainer 2026-11-19.

### D-34 Slack bot tokens per tenant in the database, encrypted with the tenant key
- **Decision:** a tenant's Slack bot token is stored in `tenant_credentials` (one row per tenant and kind, `slack_bot` first), encrypted with the tenant's payload key — the codec's AES-256-GCM cipher, the tenant ID as associated data, the same shape as the Notion webhook token (D-32). Every process resolves the token through one resolver: the credential row first, the environment variable the tenant's settings name when no row exists, so a local single-tenant run is unchanged. A key miss reloads the keys once; a row that cannot be decrypted is a setup error naming the tenant and key version, never a value, and never a silent fallback to another token. The Slack OAuth install ("Add to Slack" on the console, OAuth v2 with the manifest's bot scopes, a single-use state cookie, a pilot allowlist `AGENTOS_INSTALL_ALLOWED_TEAMS` that refuses every install when unset) creates the tenant row, its key, its token and its first admin in one unit of work, audited as `install`; a reinstall replaces the token (audited) and creates nothing else. An installed tenant has `default_agent` NULL and no Notion: the gateway answers its messages with one fixed not-set-up reply (no model, no Notion call), and a tenant with no Notion token is served Slack-only. Processes start on an empty tenants table and serve none until the next refresh; an activity for a not-yet-loaded tenant is retryable within the shared retry policy (5 attempts, about 15 s), which outlasts the worker's 5 s refresh.
- **Why:** Add to Slack must create a working tenant with no manual step (D-33's reason): a token a person exports per tenant is a per-customer manual step and a redeploy. One click in Slack plus one allowlist entry for the pilot is seamless; the database row plus the directory refresh scales to any number of tenants. The allowlist keeps the pilot bounded without a per-tenant setup step.
- **Consequence:** the app role can SELECT, INSERT and UPDATE `tenant_credentials` (no DELETE until an uninstall flow exists); row-level security hides every tenant's row from the others. A reinstall stores the new token; processes rebuild the tenant's client from it on their next read (whether Slack retires the old token is Slack's side of the reinstall). The master key (D-33) now protects bot tokens as well as histories: losing every master version loses the stored tokens too, and a reinstall is the recovery. The fixed not-set-up reply names `AGENTOS_CONSOLE_URL`, which the gateway must therefore also be given, and the app's name from the manifest's `display_information.name` ("This app" when it has none). Each worker sync reads each served tenant's credential row; this moves to change detection with the key refresh (D-33). Decided by the maintainer 2026-11-19.
- **Amended by D-36:** the app role also has DELETE on `tenant_credentials`: Disconnect in the console removes the tenant's Notion row (the only flow that deletes a credential). A Slack uninstall flow is still to come.
- **Amended by D-39:** the uninstall flow deletes the tenant's `slack_bot` row (the Notion row is kept), and a reinstall re-enables a disabled tenant.

### D-35 One broken agent never stops the worker
- **Decision:** the worker checks every published agent's Notion grants at start-up and on the directory refresh, with the same read-only check a publish runs (`grant_checker.py`). An agent whose grants fail — a database or page missing or not shared, a mapping that does not match the live schema, a missing property ID, or a tenant with no Notion token while its agents grant Notion objects — is marked **unavailable** in `agent_health` (one row per tenant and agent: the version checked, the status, a reason naming the grant and the problem, and when it was checked). A message routed to it gets one fixed reply ("… is unavailable right now: an admin needs to fix its access. Nothing was changed."), with no model call and no Notion call; a write waiting for approval is refused at Submit with the same reason, through the existing pre-write check. Every other agent and tenant keeps running. Platform-wide problems still stop start-up: no usable master or tenant key, a schema behind the code, a model with no price, an inconsistent tenants table, routing that names an unpublished agent or a channel outside its audience. Each transition is audited as `agent_health` and told once in a Slack DM — the agent's creator and the tenant's admins when it goes unavailable, the creator when it recovers. An unavailable agent is re-checked at most once every five minutes on the directory refresh; a newly published version is checked at once; a passing check marks the agent available again, without a restart. A transient Notion failure (network error, rate limit, server error) is not a grant problem: it changes no health, and the next check tries again. A check that cannot run never stops the worker or skips the other agents: a permanent connector problem (a granted database with no data source) marks its agent unavailable with the problem named; any other unexpected error is logged with the tenant and agent IDs and changes no health; the containment is per agent and per tenant, at start-up and on the refresh. A watch on an unavailable agent keeps polling — the poll fails retryably, like a connector switched off — and reports the status change once a check makes the agent available again. A task whose agent becomes unavailable between the pre-write check and the write stops clean with the fixed reply on the card, never a failure line.
- **Why:** on Railway one published agent's placeholder database ID exited the whole worker at start-up; with many tenants, one customer's broken agent would stop every tenant. Per-agent health is seamless — the people accountable are told what to fix, everyone else keeps working, and recovery is automatic — and scalable: no per-tenant manual step or restart, and the re-check bound plus Notion's rate limiter keep the reads bounded as agents grow.
- **Consequence:** health is a health state, not an admin's intent: the kill switches (D-22) stay separate, are checked first, and turning an agent off is not a health transition. The gate reads health on every step, with no cache; an unreadable health row fails the step closed, like an unreadable switch. The transition DM is best-effort: a crash or a Slack failure at the transition loses that one notice; the health state and the audit row are unaffected. The worker is the only writer of `agent_health`; the console reads it (the status display ships with the tenant-settings work). A publish that fixes the grants is noticed by the version change on the worker's next refresh pass (about five seconds), which re-checks and recovers the agent. The app role can SELECT, INSERT and UPDATE `agent_health`; row-level security hides every tenant's rows from the others. Decided by the maintainer 2026-11-20.

### D-36 Notion tokens per tenant via OAuth, and tenant settings in the console
- **Decision:** the admin settings page (`/ui/<tenant>/settings`) connects the tenant's Notion workspace with the existing public integration: a workspace admin authorizes it (`owner=workspace`), the callback validates the returned workspace bot token with one cheap call (`users/me`) and stores it encrypted in `tenant_credentials` as kind `notion`, with the workspace ID and name on the tenants row. Reconnect replaces the row; Disconnect deletes it (the app role gains DELETE on `tenant_credentials`). Every process that passes the Notion resolver reads the token the same way as the Slack bot token (D-34): the credential row first, the environment variable the tenant's settings name when no row exists; a tenant with neither is served Slack-only. The page also sets the default agent and the channel routing, validated like the YAML import (published agents, channels inside the agent's audience) and audited `tenant_settings`, and reveals, confirms or clears the webhook verification token exactly as the host command (D-32), audited `webhook_token` as the user. Connect and Disconnect are audited `connector`; no audit row holds a token.
- **Why:** a pasted integration token is a per-tenant manual step (copy it from Notion, paste it, export or store it); OAuth is one click by a workspace admin, and the encrypted row plus the directory refresh scales to any number of tenants with no operator step. Reusing the picker's integration, state mechanism and callback path means no second redirect URI to register.
- **Consequence:** the console rebuilds its Notion client when the credential changes, on its next read; the worker's start-up and registry sync resolve the Notion token alongside the Slack one, so a token connected while the worker runs rebuilds that tenant's client on the next refresh, and the health check reads it from the same registry. The host grant-check command resolves it the same way. A workspace already used by another tenant is refused (the tenants row's unique workspace). The settings page is admin-only in `ControlPlane`; a creator cannot read or change it; it reads the tenant row fresh, so a routing change shows at once and an unchanged resubmit records nothing. The webhook token's console steps share the CLI's state machine and audit kind, so the two surfaces cannot drift. Decided by the maintainer 2026-11-19 (Connect Notion by OAuth; webhook confirm in the console).

### D-37 The platform's task record and the my_tasks read tool
- **Decision:** the `tasks` table (migration 035) holds one row per task: the tenant, the task ID (the workflow ID), the requester, the agent, the item's title and link, the page it watches, the listed state, the last known status, when the task last reported (`updated_at`), and the thread it lives in. The task workflow records each state change through `record_task_state`, an idempotent upsert by task ID, behind the `task-record` patch marker; histories recorded before it replay unchanged and those tasks simply have no row. The activity reads the title, link and page from the write's stored result or the stored draft, so they never pass through workflow history; a record that fails is logged and never ends the task. The workflow's eight states map onto six listed ones: `drafted` and `awaiting_approval` list as awaiting approval, `executing` as filed, `expired` as cancelled (it closed without a write, as a declined one does), and `watching`, `done`, `failed`, `cancelled` list as themselves. `my_tasks` is a read tool in a new `platform.yaml` manifest, offered only to an agent with a write grant (a Notion database), because only such an agent starts tasks; the grant is checked again when the call runs, so a call the model invents for an agent without one is a tool error and lists nothing. It takes no input: the requester comes from the runtime, and the store lists that person's tasks made through any agent in the workspace — open ones first, then newest, at most 10 — with no Notion call. The output is wrapped in `<items>` like the other item reads, so the untrusted-data rule covers the titles. A connector switch stops only that connector's tools: `my_tasks` belongs to the platform manifest, so the Notion switch does not refuse it (knowledge search still is refused, because it reads through Notion); an agent switch and agent health stop it like every other effect. In the task's own thread, the tool first pokes the watch through the webhook's own `external_update` signal (behind the `my-tasks` patch marker) and waits, bounded and best-effort, for the task's next report; the watch answers a poke at most once per `POKE_GAP`, so a question never forces a sooner poll. A poke-answered poll records even when nothing moved, so the wait can see the refresh land. A turn refreshes at most once — a second `my_tasks` call in the same turn lists the store without another poke and wait — and a task that reported within `POKE_GAP` of the question is fresh already, so its poke and wait are skipped; both rules sit behind the `my-tasks-once-per-turn` patch marker, and histories recorded with `my-tasks` alone keep the original poke and wait on every call.
- **Why:** "where is my request?" must be answered from the platform's own state, seamlessly — one question in any thread, no Notion search, no console — and scalably: one indexed row per task, written by the workflow that owns the state, read by a tenant-scoped query, with no per-tenant step. The store is the runtime's copy, never the model's: the requester is pinned by the runtime (D-17), and the model can neither choose whose tasks it lists nor write a row.
- **Consequence:** the app role can SELECT, INSERT and UPDATE `tasks`; row-level security hides every tenant's rows from the others. Nothing deletes a task row yet (retention does not cover `tasks`; the rows are small metadata). The thread link in the listing is Slack's universal channel link (`app_redirect`), because a thread permalink needs the workspace's domain, which the runtime does not store; a true permalink is a later choice (store the domain at install, or look it up). A question asked within `POKE_GAP` of the task's last report is answered from the store at once; a question about a staler record waits up to `POKE_GAP` plus the poll's time, bounded, and a task that does not report in time is listed as it was last recorded. A task that closed between the lookup and the poke already recorded its final state, so the failed signal changes nothing and the turn still answers. Tasks recorded before the patch have no row and are invisible to `my_tasks`. The worker's start-up must wire the Postgres store (`tasks=PostgresTaskStore(pool)`); without that wiring the default in-memory store serves, which is what fakes and tests use, and production rows would not persist.

### D-38 Answer feedback is the user's action
- **Decision:** every final answer carries 👍/👎 buttons (notices, approval cards, the not-set-up reply and the fixed off/unavailable/budget replies carry none). A click is handled by the gateway, like a saved Edit form: the vote is stored in `answer_feedback` (one row per tenant, conversation, answer ts and voter; migration 036) and audited as `feedback`, with no workflow, no model call and no connector call. The voter is the Slack user of the signed request, never a field of the button value or the model; the value carries references only (the conversation ID, the answer's ts, the agent and version that answered), and a click naming another tenant's conversation is refused. A second click by the same person replaces their vote and clears its reason; another person's vote is separate. A 👎 opens a modal for an optional one-line reason (≤ 300 characters); submitting or dismissing keeps the vote, and a reason attaches only while the vote is still a 👎. The voter is acknowledged ephemerally ("Thanks — noted."); nothing is posted in the thread.
- **Why:** feedback is a person acting on an answer, not an agent acting for them, so the agent-effect gate (D-22) does not apply — an admin turning an agent off must not stop people rating the answers it already gave. One click in Slack, where people already are, is seamless; one row per vote with the tenant's existing retention purge scales with no per-tenant step. Keeping the reason out of the audit log keeps the log IDs-and-hashes-only, and purging it with the row bounds the only free text the feature stores.
- **Consequence:** the app role can SELECT, INSERT, UPDATE and DELETE `answer_feedback` (DELETE is the retention purge); row-level security hides every tenant's rows. Every click is audited: the audit key names the answer, the voter, the vote and the vote's time, so up → down → up records three events and an identical double click records twice (Slack does not retry clicks); the reason form records nothing new. The vote row and its audit event commit in one transaction (a unit of work holding the tenant's advisory lock, the control plane's pattern), so a failed audit insert leaves no vote behind and the click is told to try again. Because Slack renders blocks instead of text, an answer with buttons carries its text in section blocks (split at newlines under Slack's 3000-character section limit, never an empty section; a cut inside a code fence closes it and the next section reopens it with the same language tag); an answer posted as a new message (a dropped progress edit) is posted first and edited once more to carry the buttons, whose value names that message's ts. That button edit is best effort: a failure is logged with the tenant ID and the posted answer stays, recorded in history, without buttons. Product shape decided by the maintainer 2026-11-19 (phase 3); the handling recorded with the build 2026-11-20.

### D-39 Uninstall disables the tenant; a reinstall resumes it
- **Decision:** the gateway subscribes to `app_uninstalled` and `tokens_revoked` (bot tokens) and handles each for the workspace's tenant, taken from the signed event's `team_id`: in one unit of work it disables the tenant row, deletes its `slack_bot` credential and records one `uninstall` audit event (the event type in `tool`, the team ID in `target`, `system:uninstall` as requester and identity, never a token). The Notion credential is kept. The event's audit key is authoritative: a retry of an event already processed changes nothing even after a reinstall re-enabled the tenant and stored a fresh token, while a new uninstall event (a new `event_id`) still acts; an out-of-order event with a different ID finds the tenant already disabled with no credential and changes nothing more. Both checks sit inside the unit's tenant lock, so two events arriving together still record one uninstall; an unknown workspace is ignored with a log line, and a `tokens_revoked` naming no bot token changes nothing. The directory names the stored-but-disabled tenants (`disabled_tenants`); the worker's sync marks them in the registry, and an activity for one refuses non-retryably as `TenantDisabled` — distinct from a tenant not loaded yet, which stays retryable (D-34). A task awaiting approval, executing or watching ends `cancelled` with no Slack post, its final state still recorded for `my_tasks`; a conversation turn fails without a failure notice, leaving history valid for a reinstall. Both sit behind the `tenant-disabled` patch marker; older histories replay unchanged. A reinstall re-enables the row in the same unit of work as the new token (audited `reinstall`); agents, settings, admins, key and data are untouched. Full deletion of a tenant's data is a later admin action, not part of uninstall.
- **Why:** removing the app must stop the tenant at once with no operator step — seamless: one action in Slack, nothing for an admin to run — and scalable: the disable plus the existing directory refresh reaches every process with no per-tenant work. Deleting the Slack token at once means no process keeps posting with a token Slack has retired. Keeping the data under normal retention makes a reinstall one click that resumes the tenant rather than a second onboarding.
- **Consequence:** the app role's existing UPDATE on `tenants` and DELETE on `tenant_credentials` (D-36) cover the flow; migration 037 adds the `uninstall` audit kind. The gateway needs the tenants store, the credentials, the audit store and a unit of work (wired at start-up); a gateway built without a database ignores uninstall events with a log line. The disabled mark is worker-local state: seeded from the directory at start-up and following it every sync, so a restart never treats a disabled tenant as not-yet-loaded. Two residual windows are known consequences. After a reinstall, the worker keeps the disabled mark until its next directory pass (one sync interval): work arriving in that window is refused as disabled — a turn fails cleanly with no notice, a task ends cancelled — and resumes normally once the sync restores the tenant. And a conversation of an uninstalled tenant stays open in Temporal, waiting, until its idle timeout (7 days) closes it or a reinstall wakes it; that wait is what lets a reinstall resume the thread. A write in flight when the uninstall lands cannot be confirmed either way (the runtime is gone): the task ends without claiming it was not filed. A pending approval whose decision never arrives ends at its expiry, cleanly and with no post. Decided by the maintainer 2026-11-20.

### D-40 The nightly re-check of a creator's access, with consent
- **Decision:** the picker's sign-in gains one consent line — "Keep my Notion sign-in so the platform can check each night that I can still see what I gave this agent." With consent, the callback stores the creator's user token encrypted in `tenant_credentials` as kind `notion_creator:<Slack user ID>` (migration 038 widens the kind CHECK; the row, cipher and resolver are D-34's), audited `connector` as `creator_consent`; a consented pick replaces the row, and "Stop keeping it" on the version page deletes it (`creator_consent_revoked`). The box is a per-pick choice: completing a re-pick with it unticked revokes the sign-in a former pick kept. Dropping a creator from the tenant deletes their sign-in in the same unit of work as the member change, audited as the same `creator_consent_revoked` with the member as target — like uninstall deletes the Slack row (D-39). Without consent the picker works as before — the token lives only for the callback request — and the nightly check marks the grant `cannot_verify`, never a suspension. One Temporal schedule per tenant (`<tenant>:creator-access-schedule`, 05:00 UTC after indexing and retention, overlap skipped) runs `CreatorAccessWorkflow`: it lists the tenant's published agents, runs one activity per agent — for each granted Notion object its creator picked, one cheap read (`retrieve_database` / `retrieve_page`) with that creator's stored token, through the tenant's Notion rate limiter, heartbeating between reads — and ends with the combined health check. A disabled (uninstalled) or unknown tenant's pass ends cleanly with zero counts before any read, never a retry. The verdict per object lives in `creator_access` (`verified`, `lost`, `cannot_verify`, `checked_at`); the pass replaces an agent's rows wholesale, so an object no longer granted leaves no row. A 403 or 404 for the creator is `lost`; a dead token (a 401) is `cannot_verify`; a transient failure (network, rate limit, server error) and any other unexpected error are no verdict — the row stays as it was. A `lost` verdict is sticky: only a successful read (`verified`) replaces it, and a `cannot_verify` never lifts it. The health check combines both sources: an agent is available only when its grants pass and no granted object is `lost`. A lost object marks the agent unavailable with "its creator can no longer see '<grant>'" through D-35's path (fixed reply, refused Submit, audit, best-effort DMs to the creator and admins); a later pass where both sources pass recovers it. Recovery from a `lost` verdict waits for the next nightly pass: the worker's five-minute re-check re-evaluates health from the stored verdicts but does not re-read the creator's access. The version page shows each grant's last verdict and when it was checked.
- **Why:** product.md promises the nightly re-check, and the picker drops the token by design, so there was nothing to re-check with. Storing an encrypted per-creator token with explicit consent is seamless — one tick at a sign-in the creator already does, no developer console or pasted key, and revoking is one click — and scalable: one pass per tenant per night, rate-limited reads, one activity per agent so a slow agent never parks the whole pass. The schedule itself is still created by an operator command, so a new tenant needs that command until schedules are applied automatically when a tenant is admitted — a separate change; until then the nightly pass is not fully hands-off. Checking only the integration's access (the alternative) cannot see a creator who lost their own access, which is the promise. A lost verdict is sticky because the check's inability to verify (no consent, a dead token) is not evidence the creator regained access: only a successful read proves that, so a revoke or a dead token never silently recovers a suspended agent. Combining both sources in one health check, rather than letting each write health alone, is what keeps a passing grant check from recovering an agent whose creator lost access (and vice versa): the two sources cannot flap each other.
- **Consequence:** the creator's token is a second secret the tenant key protects (D-33): losing every master version loses it too, and a consented pick is the recovery. The token is never logged, audited or shown; the consent row's target is the creator's Slack ID. A creator who revokes the integration in Notion itself (not via the console) leaves a dead token: its reads answer 401, which marks the grant `cannot_verify` — never a suspension, and never lifting a `lost` verdict already stored; a consented pick replaces the token and the next pass verifies again. `cannot_verify` never suspends, so an agent whose creator never consented keeps working with the admin's approval as its only check, as today. The nightly pass also re-runs the grant check for every published agent (one extra read pass per night, rate-limited), which is what lets a single combined evaluation decide health with no second writer and no flap. Each creator's Notion client is closed after the pass. The schedule is created by `python -m agentos.creator_access --schedule`, as retention's is; until then no nightly pass runs. Decided by the maintainer 2026-11-20 (consent at the picker, encrypted per tenant; suspension and notification through agent health); the sticky verdict, the dead-token and disabled-tenant rules, the per-pick consent, the member-change deletion and the per-agent batching added by the orchestrator 2026-11-20 after both reviews.

### D-41 The nudge: one card, a comment and a DM, each once
- **Decision:** the stale notice gains a "Nudge the assignee" button, offered only when `follow_up.nudge` is true, under `max_nudges` (default 2, at most 10) nudges already run, and the assignee is not the requester. The button carries the task ID and a fresh offer nonce; only the requester's click on that nonce starts a nudge, once per stale period. The click drafts a nudge task — a child `TaskWorkflow` with tool `nudge`, `ABANDON` as parent-close policy, so the watch keeps polling while the card waits — whose draft freezes the comment text, the item, the assignee resolution and the requester's display name. One approval card previews both effects exactly (the comment with its mention, the DM: "<requester> asked me to check on '<item>'", the item link, the approved text, nothing else from the conversation), with Submit / Edit / Cancel like other writes; an edit changes the text both effects carry. On approval the comment runs first through the existing comment path (reference marker + `external_writes` lease + reconcile), then the DM through the Slack post path (metadata marker + lease + history lookup in the DM channel opened with `conversations.open`). A DM failure after the comment reports "commented, couldn't DM" and never retries the comment. Both effects pass the agent-effect gate; a nudge that ran restarts the stale clock from the nudge, and the next stale period may offer again. The assignee is an optional `assignee` people property per database grant (first person only), addressed by its property ID like the other roles: Notion user → email (the integration's user-email capability) → Slack user by `users.lookupByEmail`. The fallbacks are decided in the card text, never by the model: no property or an empty one → a comment without a mention; no Slack match → a comment with a plain-name mention and no DM; the assignee is the requester → no offer. Audited as one `approval` (tool `nudge`) plus one `write` per effect (tools `nudge_comment`, `nudge_dm`); declined or expired as `approval_closed`. All new workflow commands sit behind `workflow.patched("nudge")`; older histories replay unchanged. Product shape decided by the maintainer 2026-11-18/19 (both effects through one card; the DM names the requester; `max_nudges` default 2; the per-agent switch); the orchestrator added 2026-11-20 that the nudge comment is never low-risk.
- **Why:** a follow-up that acts must stay seamless — one click on the notice already in the thread, one card that shows exactly what will be sent, no console step and no pasted ID — and scalable: the offer, the approval and the two writes ride the task machinery every tenant already runs, the people lookup shares the tenant's cached Notion user list, the bound on nudges and the one-offer-per-period rule keep a stale item from paging anyone forever, and the child task lets the watch keep watching while a card waits up to the approval window.
- **Consequence:** the DM match needs the Notion integration's "Read user information including email addresses" capability; without it the assignee's email is invisible and the nudge falls back to a plain-name comment with no DM (a maintainer step, not a per-tenant one). The Slack scopes it needs (`users:read.email`, `im:history`) are already in the app manifest. A configured assignee mapping is held to the same grant check as the other roles (a people property, an ID configured), but a broken one disables only the nudge, never the agent: it is reported in the console's grant check and the health log, and the nudge then treats the mapping as absent (a comment without a mention). The mapping counts as a property change in the access diff, so adding it is a widening the approver acknowledges. The nudge task records its own row in `tasks`. A declined, expired or failed nudge spends the period's offer without restarting the clock, and a spent offer (clicked, prepare failed, nudge done) drops its button from the stale notice, best-effort; the watch may end while a card waits, and the nudge then still runs (its report to the watch is best-effort). A DM Slack refuses for good (a gone channel or user, an inactive account) is audited as a `write` error and not retried. The DM's exactly-once lookup needs DM history; where Slack refuses history the post path's accepted residual applies (a retried post can repeat, logged).

### D-42 The worker ensures every served tenant's nightly schedules
- **Decision:** the worker ensures each served tenant's three nightly schedule kinds — one index schedule per granted scope (03:00 UTC), retention (04:00 UTC) and creator-access (05:00 UTC) — with no operator step. One place does it (`agentos/schedules.py`, `ensure_tenant_schedules`), over the modules' own idempotent create-or-update helpers. It runs at start-up for every served tenant, before the worker polls, and on the directory cadence (the same 5-second pass as the tenant sync and the health refresh): a tenant the sync just admitted, a reinstall brought back, or a published page grant changed is ensured on the next pass. The pass compares a fingerprint of the tenant's granted scopes (scope to root page, from its published agents), so an unchanged tenant — including a publish that changes no page grant — causes no schedule call; a changed one re-applies its index schedules. A tenant's fingerprint is recorded only after its apply succeeded, so a failure is logged with the tenant ID and retried on the next pass; one tenant's failure never stops the pass, another tenant, the worker, or serving the tenant. A tenant no longer served loses its record, so a reinstall re-ensures even with unchanged scopes. A disabled (uninstalled) tenant's schedules are left as they are — not paused, not deleted: its runs already end cleanly (D-39 for tasks and turns; the creator-access pass ends with zero counts before any read; a leftover index run refuses before any connector call). Stored pages of revoked scopes are not purged automatically; `index_knowledge --schedule` (which passes the knowledge store) remains the repair that does. The three `--schedule` commands stay, as a manual repair. Amends D-40's operator-step consequence, and retention's and indexing's matching practice.
- **Why:** the schedules existed only after an operator ran `--schedule` per module, so a tenant added by "Add to Slack" got no knowledge refresh, no retention purge and no access check — a per-tenant manual step, which the product rule forbids. Seamless: installing the app is the only step; the schedules follow the tenant, its grants and its reinstall with nothing for an admin to run. Scalable: one pass over the served tenants on the cadence the worker already keeps, no per-tenant manual work as tenants grow; the fingerprint bounds schedule calls to actual scope changes, and the per-tenant failure isolation keeps one bad tenant from parking the rest. Leaving a disabled tenant's schedules alone (the alternative: pausing them) keeps the uninstall path one action with no schedule bookkeeping, and the runs are already safe; a reinstall re-ensures, so nothing stays stale.
- **Consequence:** start-up does one ensure pass per served tenant (a list plus create-or-update calls), logged and non-fatal per tenant; the refresh task is cancelled with the other refreshers at shutdown. No workflow code changes: the schedules start the existing `IndexingWorkflow`, `RetentionWorkflow` and `CreatorAccessWorkflow`. The first-page-grant gap remains: a worker started with no page grants builds no embedder and registers no indexing workflows until it restarts, so a deployment's first page grant still needs one restart (the schedule itself is ensured regardless). `apply_schedules` still lists every schedule ID to plan one tenant's creates, updates and deletes by the tenant's prefix — fine at today's scale, a full list per changed tenant; a per-tenant list filter is the lever if the schedule count grows. Recorded with the build 2026-11-20; the product rule it applies (no per-tenant manual step) is the maintainer's.

### D-43 Approval policy per low-risk action
- **Decision:** the design rule becomes: writes never run without approval from the requester, unless an admin turned approval off for that low-risk action; what was approved, or what the policy allowed, is exactly what runs; every external write is idempotent. The manifest carries a `low_risk` flag, accepted only on a comment action (loading refuses it on any create, append or replace); today only Notion's `add_comment` has it. The policy is one row per tenant and action (`approval_policies`, migration 040): `requester_approval` (the default, also for an action with no row) or `none`. An admin changes it in an Approvals section on the settings page, audited as `policy_change` with the admin's identity; a creator cannot. At run time the task asks the policy once, after the comment's item is resolved: when the policy is `none` and the item was filed by the requester — the page's link to the task that created it and that task's requester, from the platform's own records, never from the model — the comment runs without a card, through the same write activity (agent-effect gate, lease, reconcile), audited as `write` with outcome `policy`, no approver and no `approval` row; the thread line reads "Commented on '<item>' (<link>) (no approval needed: your admin's setting)." A refused write (a switch, a broken grant) records `write` with `error` and no approval row, and the thread says why. In every other case — the default policy, an item the requester did not file, an item with no creating task, any create, the nudge's comment — the card shows as today. The new workflow commands sit behind `workflow.patched("approval-policy")`; older histories replay unchanged.
- **Why:** seamless — the requester approves nothing extra: a comment on their own request just runs, with one line saying why, and the admin's whole setup is one switch on the page they already use; the default stays safe, so nothing changes until an admin chooses. Scalable — one row per tenant and action, no per-agent setup and no operator step; the decision reads stores the worker already has, and the write rides the same exactly-once machinery every tenant already runs.
- **Consequence:** the audit log's outcomes gain `policy` (a write that ran under the policy, beside `ok` and `error`); a policy-allowed write has no `approval` row, so the log alone shows it ran without approval. The policy is read once per comment task, just before the write; an admin's change lands on the next task, not on one already running. The policy path runs the same pre-write audience and channel-pause re-check as a carded write, just before the write and without the approval row: a channel paused or an audience lost while the task runs stops the comment, and the thread carries the line the card would show. The model is still told a card was sent when a write becomes a task; the thread line corrects it when the policy runs the comment, linking the item. The Drive comment joins the flag when the Drive connector adds it. Design-rule change approved by the maintainer 2026-11-19; the nudge's comment never low-risk (D-41, orchestrator 2026-11-20).

### D-44 Creator test sets, run against the draft
- **Decision:** each agent version carries test cases — a question and one expected behaviour: answers citing a granted page, drafts a write to a granted database, refuses, or hands off to a listed specialist. Cases are written on a draft (the expectation may be left unset for the creator to choose), stored per version, and copied forward when a new draft is made from a version. The agent's creator and admins run the draft's cases (role check in the control plane); a run needs every case's expectation chosen and, with the picker required, every grant new since the published version chosen from the creator's own Notion — the submit rule, checked again at run time (maintainer, 2026-11-20). One run of a version goes at a time: a second start while one is running is refused, and a retried start with the same request ID returns the first run; the check and the row's insert share the unit of work's tenant lock, so two starts never interleave. A dedicated workflow on its own task queue runs each case as a turn against the **draft** definition — the same `call_model` and read-tool path as a real turn, pinned to the draft version and reading with the draft's grants — in a conversation of its own, with the runner as the requester in a direct message. The draft's own audience is not checked: its editors may test it whatever audience it sets. Writes never run: a drafted write is recorded (task kind and target database, resolved with the draft's grants) and stops the case; a hand-off is recorded and stops the case too. No card, no task, no Slack post. The run's spend counts in the tenant's usage and is capped at $0.20 (maintainer, 2026-11-19): a check after every model step stops the run at the cap, unknown spend stops it too (D-21), and the cases not run are reported; one call may take the run past the cap by its own cost, the bound the monthly budgets keep. The aggregate bound is the monthly budgets plus one run at a time per version. Each case is judged pass/fail with a fixed reason (expected source not cited, wrong action, did not refuse, wrong hand-off) from what the turn observably did: the pages its final answer cites, the write it drafted, the agent it handed off to, or a refusal — the provider's `refusal` stop reason only. A platform stop is not a refusal: a final reply that is one of the runtime's fixed stop texts (a reached budget, an agent switched off or unavailable) ends the case as an error with its own code (`stopped_by_budget`, `agent_off`, `agent_unavailable`), so a REFUSE case never passes on a reply the agent never chose. The run's row always closes: an uninstall mid-run (`TenantDisabled`) or a failure that ends the run closes it as failed, best-effort with one short attempt, so the console never waits on a run that ended. The version page shows the cases, the run button and the latest run's results with its time and spend; the approving admin's pending view warns when there is no run or the definition or the case set changed since it ran (the run records both hashes it ran against; a withdraw and resubmit alone changes neither). The feedback page's "Make a test case" button adds a stored question to the agent's next draft — its newest draft, or one made from the published version when none exists — with the expectation left unset; only a user message of a conversation an audit row ties to this agent qualifies, so another agent's conversation or an assistant message is refused. Cases and runs are audited (`test_case`, `test_run`) with references and hashes only; a run's reads stay out of the audit log the feedback page reads, so a creator's tests do not pollute the agent's feedback. Migration 041 adds `test_cases` and `test_runs` under row-level security.
- **Why:** a creator must see that an agent works before submitting it, and an admin must see the evidence before publishing — seamless: cases are written on the same page as the definition, one button runs them, one click turns a bad answer into a case, and the approver's warning is on the page they already review; scalable: runs are queued per tenant on their own queue with a dollar cap, no operator step, and the results are references the console reads without a model call. Running against the draft (the alternative: the published version) is what makes the test useful before publish; reading with the draft's grants is what makes a narrowed or widened grant visible in the results. Stopping at the drafted write keeps the run free of external effects while still testing the write path's decision; judging from observable references (not a second model call) keeps the verdict cheap and deterministic.
- **Consequence:** a model's plain-text refusal ("I can't help with that" with a normal stop reason) is not detected as a refusal — only the provider's `refusal` stop reason is; the runtime's fixed stop texts (a budget, a switch, the agent's health) end the case as an error, not a refusal. A creator testing a prompt-level refusal convention needs a detection rule this build does not have (options: a prompt convention the judge matches, or a judging model call with its own spend). The run's conversations are purged by the normal retention; the case rows live with their version (a deleted draft's cases go with it), and run rows are kept like the audit. A run snapshots its cases at start: a case added mid-run runs next time. A draft is read fresh on every model step (only immutable versions are cached), so a prompt edited between two runs takes effect in the second; an edit mid-run takes effect mid-run. The console connects to Temporal on the first run, so it starts and serves every other page with Temporal down; a run that cannot start is closed as failed and shown as such, and the console drops its Temporal client at shutdown (the SDK has no close API; the reference is released). The run's workflow carries a one-hour execution timeout, and a running row older than that plus ten minutes is shown as failed on the version page and closed as failed by the next run start, so a run whose workflow died or whose final write could not land never blocks the version. Recorded with the build 2026-11-20; the cap and who may run are the maintainer's (2026-11-19); the run-time pick check is the maintainer's (2026-11-20), and one run at a time, platform stops as errors and the always-closing row were decided in the review fix pass (2026-11-20).

### D-45 Google Drive: one service account per tenant
- **Decision:** an admin connects Drive on the settings page with one click; the deployment's Google service account creates a service account for the tenant in the deployment's project (`projects.serviceAccounts.create`; a 409 finds the account a retried connect already made), and the connection row and its `connector` audit event (`drive_connect`, the account email as target) commit in one unit of work after the Google call succeeds. The account ID is deterministic from the tenant ID (`ids.drive_account_id`, a hash in Google's 6–30-character class), so a second click, a retry after a lost response and an overlapping attempt all find the same account and record one event. Connect, disconnect and the Drive part of uninstall hold the tenant's unit-of-work lock across the Google call and the row write, so the Google-effect-and-row pairs serialize across processes and never leave a row without an account or an account without a row; the IAM create and delete calls carry a 10-second timeout because they hold a pool connection. Disconnect deletes the account at Google by the row's stored email — a project move must not orphan the old account — and the row (a 404 — already gone — still clears the row), audited `drive_disconnect`; with no row it still deletes the derived account (an orphan a failed connect left) and records nothing. Uninstall deletes the row with the disable and always tries the account delete when Google is configured — the row's email, else the derived ID — best effort under the same lock, logged with the tenant ID, never blocking. A create answered 409 whose get answers 404 is a delete still propagating (the IAM API is eventually consistent): `recently_deleted`, plain words asking to try Connect again in a few minutes; re-creating the ID is Google's documented path, while undelete is a conditional last resort that restores the old identity — not what an intentional disconnect wants. The settings page shows the address to share with (a copy button), what the account can see now — the first 100 items, files and shared drives together, with a note when more are shared (`files.list` with `sharedWithMe` plus the shared drives it is a member of; names, IDs and links only) — and the status and the last error in plain words. The GET writes nothing: the live check's outcome is shown, not stored, and the row's status is written only by connect and disconnect (a later polling check records checks). One deployment service account — its JSON key in `GOOGLE_SERVICE_ACCOUNT_KEY`, the project in `GOOGLE_PROJECT_ID`, both deployment settings — mints short-lived Drive tokens for the tenant accounts through the IAM Credentials API (`generateAccessToken`), cached until shortly before expiry and evicted when the account is deleted or re-created; no key is created or stored per tenant, and the connection row is not a credential. A 2xx body missing a field or not JSON reads as `unavailable`; a 400 as `refused`; a 401/403 names the deployment account's role on an IAM call and the tenant account's refused access on a Drive call. With either setting unset, Drive is not set up on that deployment: the section says so and offers no button. Migration 042 adds `drive_connections` (tenant_id primary key) under row-level security. The maintainer's one-time Google Cloud setup is in operations.md.
- **Why:** seamless — the customer's whole setup is one admin click plus one share: no Google Cloud console steps for the customer, no keys to paste, and the page shows exactly what the agents can see; the end user shares a folder with an address as with any colleague. Scalable — accounts are created automatically, one per tenant, with no per-tenant manual step and one deployment key to operate; each tenant has its own identity, so each has its own per-user Drive quota bucket (the shared-account limit the spike memo named), and tenant isolation needs no sharer-matching rule: whatever the tenant's account can see is the tenant's, and another tenant's account cannot see it. The alternative — one shared agent account for all tenants — fails the quota criterion and needs a matching rule to keep tenants apart; per-customer OAuth consent fails both criteria (restricted-scope verification plus an annual security assessment on us, or a per-customer admin trust step).
- **Consequence:** a project holds about 100 service accounts by default — one per connected tenant; raise the quota on request or add projects before the product outgrows it (a second project changes new tenants' addresses; the account ID stays deterministic per tenant, and a disconnect after a move still deletes the old account by its stored email). Service accounts created after 2025-04-15 cannot own Drive files, so create-from-template (a later write) is limited to Workspace shared drives (maintainer, 2026-11-20); the end-state account (our own Workspace domain) is still open. The deployment key carries Service Account Admin and Service Account Token Creator on the project: one secret to guard, never logged, never in a repr. The deployment account can see every tenant account it created (it administers them), but Drive reads run as the tenant account's minted token, never the deployment's. The settings page's list check is a read of Google that writes nothing: a transient failure shows as an error in plain words for that view only, and the row's status changes on connect or disconnect alone. The list shows at most the first 100 items and says so when more are shared; the deployment lock covers only the IAM calls (create, delete, mint), and Drive lists page on a session per call, so one tenant's list never waits on another's. A reconnect right after a disconnect can meet `recently_deleted` while Google finishes the delete: a few minutes' wait and a second click connect, and the re-created account is a new identity — the old account's sharing and roles do not carry over. Recorded with the build 2026-11-20; the per-tenant account model and the deployment-key mechanism are the maintainer's (2026-11-20), and the review fixes (the lock across the Google call and the row write, the read-only GET, the 100-item cap, delete by stored email, `recently_deleted`) are the maintainer's (2026-11-20).

### D-46 Drive read: any creator picks what is shared with the address; the nightly walk keeps it in sync
- **Decision:** Drive becomes a second knowledge connector beside Notion. A creator grants a folder, a file or a shared drive by picking it from what the workspace's Drive account can see (the capped D-2 list) on the version page — one click adds it, one click removes it. There is no per-creator Google sign-in and no pick gate: the Notion `_require_picked` rule does not apply to Drive grants, because the check is the admin's approval at publish, not the creator's own access. The settings page and the version page say plainly: "Anything shared with this address is available to every agent creator in this workspace; an admin approves each agent before it reads it." A grant is one scope (`drive:<id>`); the index reuses the knowledge tables (a Drive file is a page, its ID the `page_id`, its `webViewLink` the link), so the tenant-and-scope filter inside the search query applies unchanged. A new `DriveIndexingWorkflow` (its own name, references only in history, continue-as-new for large folders) walks each granted folder recursively — or the one granted file, or a shared drive from its root — on the same nightly schedule mechanism as Notion (one schedule per Drive scope, ensured by the worker; `index_knowledge` runs Drive scopes too, `--schedule` and `--confirm-gone` included). Docs and Slides export to plain text; a Sheet exports every tab as CSV with the tab's name kept as a heading; other types are skipped and counted. A file whose Drive `version` is unchanged is not re-exported. Files no longer seen in a complete walk, trashed, or no longer readable (a 404, or a 403 whose reason is lost sharing) are removed; a walk that could not see everything — a failed folder, a truncated listing, the discovery cap — prunes nothing that run. A quota 403 (`userRateLimitExceeded`, `rateLimitExceeded`, `quotaExceeded`) is retried with the wait Google asked for; a disabled-API 403 (`SERVICE_DISABLED`, `accessNotConfigured`) is a lasting failure: the file is failed and kept, not gone. A scope whose root is gone or unreadable — any failure, not only a gone one — is pruned only after Notion's repeated-run guard, never on one run's evidence. A failure anywhere in a file's pipeline — export, embedding, storage — is retried by Temporal when transient and, if it lasts, counted in the summary (folders included) — never silent, never failing the whole run; what is stored for the file stays. The walk's outcome is recorded on the Drive connection row (`record_check`): `error` with a code when any node failed, `connected` otherwise. Before a Drive hit is cited it is confirmed live with the tenant's token (`files.get` with the file's parents, walked up to the granted root; a file gone, trashed or moved out of the scope drops it, as the Notion re-check drops a page that left its root); the citation links to the file, and a sheet passage names its tab. The Drive connector switch covers Drive indexing and the Drive part of search; a Notion scope answers to the Notion switch, a Drive scope to the Drive switch. v1 keeps Drive in sync by this nightly walk, not the Drive changes feed: one fewer stored cursor per tenant, and the walk already finds deletions and lost access. The picker opens folders and shared drives one level at a time (each page lists one level, capped like the top level), so one share of a shared drive is enough to pick an item inside it; The picker reads a drive root with `drives.get` and lists it drive-scoped, and reads and lists a folder unscoped (a `drives.get` 404 means a folder), the same calls the indexer makes; Google refuses a folder the account cannot see; every ID the picker takes must be shaped like a Drive ID and is refused before any Google call otherwise; and choosing accepts only an ID (posted as the ticked item's ID, not its position) that is in the re-read listing of the folder it was posted from.
- **Why:** seamless — the customer's whole setup stays one admin click plus one share (D-45); a creator then grants what is shared in one click with no Google sign-in, no developer console and no pasted ID, and the admin's publish approval is the only gate. Scalable — the index rides the knowledge tables, the nightly schedule and the embedding/budget/usage path every tenant already runs, one workflow per scope with no per-tenant manual step; the version comparison re-exports only what changed, and the walk (rather than a per-tenant changes-feed cursor) finds deletions and lost access with no extra stored state. Picking only what the creator can personally see (the Notion model) would need a per-creator Google sign-in — a second onboarding step the product rule forbids — and would not match the tenant-account model where whatever is shared with the address is the tenant's. The changes feed (the alternative) would add a stored cursor per tenant and a second sync path to reconcile; the nightly walk is simpler and already covers removals, at the cost of changes appearing on the next nightly run rather than within seconds.
- **Consequence:** changes to a shared file appear in answers after the next nightly run (not within seconds like a Notion webhook page refresh); there is no Drive webhook in v1. Anything shared with the address is grantable by every creator in the workspace, so the admin's publish approval (and the widening acknowledgement) is the control — the version page and docs state this plainly. A Sheet is indexed as one page per file with its tabs as headings, so a citation names the file and the passage names the tab; per-tab links are a later refinement. A shared drive is picked as its own kind and walked from its root (`drives.get`, then a drive-scoped `files.list`); a Workspace customer adds the workspace's Drive address as a member (Viewer for reading) of the shared drive — that is the one share. The Drive read scope (`drive.readonly`) authorizes the Sheets API reads used for the tab export. The re-check walk (and the comment path's `resolve_item`, D-47) matches the granted root by ID and never fetches it: a shared drive's root is not a file, `files.get` of it answers 404, so a file in a granted shared drive is confirmed and resolved without a read of the root (review fix, 2026-11-21). The connector offers the model no Drive tools yet; the writes arrive with their own tickets. Recorded with the build 2026-11-20; the picker model (any creator, admin approval at publish, no pick gate) and the nightly-walk sync (no changes feed in v1) are the maintainer's (2026-11-20).

The header and the card bounds are bounded so Slack always fits: at most 50 columns, each name at most 200 characters, each cell at most 1000. No workflow command changes for an existing history: the new kind and activities are reached only by an `append_row` spec, which no older task carries, so no patch marker is needed; a `drive_append` replay scenario is recorded. The review fixes (2026-11-21): cells land exactly as approved — a text cell is sent as `stringValue` inside `appendCells` and stored literally, never parsed into a formula or another type (the typed `ExtendedValue` union, developers.google.com/sheets/api/reference/rest/v4/spreadsheets/other#ExtendedValue; parsing "as if the user typed them into the UI" is the values API's `USER_ENTERED` option, which `appendCells` does not use, developers.google.com/sheets/api/reference/rest/v4/ValueInputOption), so a cell like `=1+1` stays text; a value the model gave as a JSON number is sent as `numberValue` and shown as that number, and an edit's values are text. The Edit form is built from the draft's columns — one input each, empty for a cell the row left out — and an edit may name any subset of them and clear a cell with an empty value; the gateway and `apply_edit` check the same set. The approved shape is the written shape: the write and reconcile refuse with the header-changed text when the draft's columns differ from the live grant's (a republish between draft and approval) as well as when the live header differs, and the row is built from the draft's columns. The Drive picker lists Sheets (their `mimeType`) and choosing one asks for its tab (one `spreadsheets.get` of `sheets.properties.title` only); the grant stores the tab and submit reads the columns as before, and the definition editor still works. The header-and-count read asks `ranges` for the granted tab alone, not every tab; a draft's or submit's header check reads row 1 only. `sheet_for` refuses a name two granted sheets share — the model must use the ID. The Sheet is picked by opening the shared drive or folder it sits in, so one share of a shared drive is enough.
- **Why:** seamless — the customer's setup stays the one share (D-45/D-46), now as Editor for the write; the creator names only the file and the tab, the platform reads the columns, and the end user approves one card that previews exactly the row, with the Edit form they already know. Scalable — the append rides the task machinery, the lease and the reconcile every tenant already runs, one `drive` scope constant serves reads and writes, and the connector is chosen by manifest, so the template and section writes that follow add kinds and tools, not new write paths.

The appended row appears in the Sheet as the tenant's agent account, never the asker, and its developer metadata is invisible in the Sheets UI and moves with the row. ### D-49 Drive write: create a Doc from a template in a granted shared-drive folder, approval always
- **Decision:** the Drive connector's third tool is `create_doc_from_template` (manifest `drive.yaml`: risk `write_irreversible`, idempotency `app_properties`, never `low_risk` — a create always asks the requester's approval). The model is offered it only when the agent has a granted template, and its description lists the granted templates with their blanks; the call names a template, the new Doc's title and a value for every blank — a missing or unknown blank, or an empty value, is refused for the model to correct, as is any value or title containing the fill sentinel's prefix (`⟦agentos-fill:`) or a raw form of one of the template's blanks (`{{name}}`, `{{ name }}`, ...): "A value can't contain a template blank like {{name}}; write it another way." The edit refuses the same markup, both in `apply_edit` and as the Edit form's error. A template write target is a grant of kind `template` (`grants.drive.templates: [{id, name, folder_id, blanks, drive_id}]`): `id` is the granted template Doc's file ID (one `drive:<id>` scope, granted for the write but not indexed as knowledge), `folder_id` the destination folder, `blanks` the template's `{{field name}}` placeholders, and `drive_id` the shared drive that folder sits in. The grant is copy-only: the template itself is not a read or comment target through it (`resolve_item` does not resolve it). The creator names no blanks and no drive — they are read once when the version is **submitted** (the template's metadata and text and the folder's metadata only, never the whole Drive) and stored as the grant's `blanks` and `drive_id`, duplicate blank names collapsing to one, so the published definition records them and the admin's `reviewed_sha256` covers them; the version page shows the blanks. Submit refuses a template that is not an untrashed Google Doc ("template '<name>' must be a Google Doc"). The destination folder must sit in a shared drive: at **publish** the folder's `driveId` is read and a folder outside a shared drive refuses with "New Docs can only be created in a shared drive folder; pick a folder inside a shared drive.", as does a grant with no shared drive recorded — the pilot's service account cannot own files (D-45), so a new Doc can only be created inside a shared drive (maintainer, 2026-11-20). The folder's shared drive is re-checked live against the recorded `drive_id` before the card (`resolve_doc_folder`) and at the write and reconcile (`check_doc_shape`): a folder moved to My Drive refuses with the publish's plain words, one moved to another shared drive refuses as a changed shape. The widening diff carries a template grant, and a changed folder or blanks reads as "uses other properties". The card previews the title, the destination folder (name and link) and every blank with its value as a two-column table; Edit changes the title or a blank's value (an empty value fills the blank with nothing; the title cannot be empty) and needs a fresh approval — the editable fields are the title and the draft's blanks, not a fixed set. The call screens to a new `create_doc` task kind on the comment path's shape — one approval card, one write, no follow-up watch — with its own prepare, write and reconcile activities; the task spec carries the manifest tool, so the write chooses the Drive connector through the registry. The write looks up first: `files.list` in the destination folder for `appProperties has { key='agentos_write' and value='<SHA-256 of the idempotency key>' }` (drive-scoped, `supportsAllDrives`, `includeItemsFromAllDrives`); a copy found and fully filled → done. Otherwise `files.copy` of the template into the folder with the title and that appProperty set in the **same** request (the copy keeps the source's mime type), then one Docs `documents.batchUpdate` filling every raw form of each blank (`{{name}}`, `{{ name }}`, ...) in two passes: each form to a unique sentinel per blank (a hash of its name in brackets, prefix `⟦agentos-fill:`), then each sentinel to its value — the value inserted literally (no markup interpretation). Because the draft and the edit refuse a value carrying a blank's form or the sentinel prefix, the passes never splice a value and a filled copy never reads as unfilled. A template with no blanks needs no fill: the copy is the finished Doc and the batchUpdate is skipped. A form or sentinel no longer present is a no-op, so a lost response between the copy and the fill leaves a marked copy the retry finds and fills again, never a second Doc. The write and reconcile refuse when the draft's blanks or folder differ from the live grant's (a republish between draft and approval) or the folder's live shared drive is not the recorded one. "With nothing written" is true only before a copy exists: when an earlier attempt's copy may exist, the thread line is "I couldn't create '<title>': <reason>" for a permanent refusal, and "I couldn't confirm whether the Doc was created; please check <folder link>" when the retries run out and reconcile's shape check refuses the look. The thread line reads "Created <title> (<link>)." The audit rows are the comment's (`approval` then `write`, tool `create_doc_from_template`, references and hashes only). The bounds keep the card and Edit form within Slack: at most 50 blanks, each name at most 200 characters, each value at most 1000, the title at most 150. No workflow command changes for an existing history: the new kind and activities are reached only by a `create_doc` spec, which no older task carries, so no patch marker is needed; a `drive_create_doc` replay scenario is recorded. The picker has two steps, each browsing folders and shared drives: the template Doc, then its destination (a folder inside a shared drive, never the drive's root: the creator picks a folder from the list or chooses "Put new Docs in this folder" for the one being browsed, and the folder is read again before the grant is added), so the two may sit in different folders; the template is read again before the grant is added.
- **Why:** seamless — the customer's setup stays the one share (D-45/D-46), now as Content manager of the shared drive for the write; the creator picks the template and the folder in the Drive picker (one click each) or names them in the definition, the platform reads the blanks and the destination drive, and the end user approves one card that previews exactly the title, the folder and every filled field, with the Edit form they already know. Scalable — the create rides the task machinery, the lease and the reconcile every tenant already runs, one `drive` scope constant serves reads and writes, and the connector is chosen by manifest, so the section write that follows adds a kind and a tool, not a new write path.
- **Consequence:** creating needs the share to allow it: Viewer on the template is enough to read and copy it, and the folder needs the address as Content manager of the shared drive — the settings docs say so. The new Doc appears in the folder as the tenant's agent account, never the asker, and its marker appProperty is invisible in the Drive UI. A template whose text changed since submit is not re-read at the write: the fill uses the blanks the definition froze, so a blank added or renamed in the template after submit is left unfilled until the creator republishes (which re-reads the blanks) — the same class of residual as the append's header, caught at submit rather than at the write. The marker lookup reads the copy's text to tell a filled copy from an unfilled one: a remaining blank form or fill sentinel reads as unfilled, and the retry fills what is left. A value that would carry a blank's form or the sentinel prefix is refused at draft and edit, so that residual is closed: a filled copy reads as done and the retry never splices a value. A destination folder moved to My Drive or to another shared drive after the publish refuses the create before the card and at the write, until the creator republishes (which re-reads the drive). One folder per template grant: the template's file ID is granted once across kinds. A tenant's no-approval policy never reaches a create: the manifest tool is not low-risk. The shape check also runs before reconcile's marker look: a republish since the draft stops the look, and the task says it could not confirm and points to the folder — never that nothing was created, since a Doc an earlier attempt landed may still be there. Recorded with the build 2026-11-21; approval always, no watch and the shared-drive-only destination are the maintainer's (2026-11-19 / 2026-11-20); the `{{field name}}` blanks and the card preview are the maintainer's (2026-11-21); the review fixes (the two-pass literal fill of every raw blank form, the editable title, the shared-drive-only destination picker, templates out of knowledge) are the orchestrator's (2026-11-21); the second-round review fixes (values and titles carrying the fill's markup refused at draft and edit, the no-blanks fill skipped, templates must be untrashed Google Docs, the destination drive recorded at submit and re-checked live, template grants copy-only, every append field multiline in the Edit form again — only the create's title is single-line) are the orchestrator's (2026-11-21).

### D-50 Drive write: replace a marked section of a granted Doc, approval always
- **Decision:** the Drive connector's fourth tool is `replace_section` (manifest `drive.yaml`: risk `write_irreversible`, idempotency `revision`, never `low_risk` — a replace always asks the requester's approval). The model is offered it only when the agent has a granted section, and its description lists the granted sections with their headings; the call names a section and the new text. A section write target is a grant of kind `section` (`grants.drive.sections: [{id, name, doc_id, heading}]`): `id` is the Doc's file ID (one `drive:<id>` scope, granted as for reads and indexed like any file), `doc_id` the same Doc's file ID named for the write (it must equal `id`, enforced at parse), and `heading` the heading the creator names, stripped of surrounding whitespace at parse. The section is everything under that heading up to the next heading of the same or higher level (a `HEADING_1` ends a `HEADING_2`'s section; a deeper heading is part of it; `TITLE` and `SUBTITLE` keep the highest level, so only another `TITLE`/`SUBTITLE` ends their section); the heading itself is kept (maintainer, 2026-11-21, replacing the named-range decision). The section must be **plain paragraphs only**: a table, an inline image or any other non-paragraph element under the heading refuses it (maintainer, 2026-11-21). The creator picks the Doc in the grant picker and chooses its heading from a one-read list of the Doc's headings (or types it); a Doc already granted as a read file shows a plain message (a Doc is granted once across kinds). When the version is **submitted** the platform reads the Doc's metadata and body (`files.get` then `documents.get`) and checks the heading exists exactly once and the section is plain paragraphs, refusing a missing heading with "I can't find the heading '<name>' in <doc>; ask the creator to update the agent", a duplicated one with "The heading '<name>' appears more than once in <doc>; ask the creator to update the agent", and a table or image with "I can only replace a section made of plain paragraphs; '<doc>' has a table or image under '<heading>'", so the admin reviews a section the agent can replace. The version page shows the heading and the widening diff carries a section grant (another Doc or heading reads as "uses other properties"). The draft step reads the section's current text (the card's "before"), the Doc's `revisionId` and the content range, and freezes them with the heading and the new text; the new text is bounded (2000 characters) and inserted literally as plain text, and a character Google Docs strips (a control character other than newline and tab, or a private-use code point) is refused at draft and edit. The section's current text is bounded too: over 5,000 characters refuses the draft in plain words (maintainer, 2026-11-21). The card previews the Doc (name and link), the section's heading, the whole before text (spread over section blocks, never silently cut) and the after text; Edit changes the new text and needs a fresh approval, keeping the same read revision. The call screens to a new `replace_section` task kind on the comment path's shape — one approval card, one write, no follow-up watch — with its own prepare, write and reconcile activities; the task spec carries the manifest tool, so the write chooses the Drive connector through the registry. The write is one Docs `documents.batchUpdate` carrying `writeControl.requiredRevisionId` = the stored read revision: it inserts the new text **first** at the section's first content paragraph (so the new paragraphs take that paragraph's NORMAL style), then deletes the shifted old range; an empty section normalises the inserted range to NORMAL_TEXT and clears its bullets (`updateParagraphStyle` + `deleteParagraphBullets`), a section ending at the body end keeps the body's final newline (delete up to end-1, insert without a trailing newline), and a heading that is the Doc's last paragraph inserts before that final newline (review fix, 2026-11-21, replacing the delete-then-insert sequence). The revision is the idempotency lock — a retry after a lost response, or a Doc someone else moved, gets a revision mismatch (a 400 `FAILED_PRECONDITION`); the Doc is then read and the section's text compared with the approved text: equal → done (the earlier attempt landed), different → refuse "The document changed since you approved; I'll draft it again" and nothing written. The write and reconcile refuse when the draft's heading differs from the live grant's (a republish between draft and approval), the heading is gone or duplicated, or the section holds a table or image; the fresh look-before-write runs the same shape check as reconcile. The audit rows are the comment's (`approval` then `write`, tool `replace_section`, target the Doc ID, references and hashes only). No workflow command changes for an existing history: the new kind and activities are reached only by a `replace_section` spec, which no older task carries, so no patch marker is needed; a `drive_replace_section` replay scenario is recorded. The Doc is picked by opening the folders and shared drives it sits in, so one share of a shared drive is enough.
- **Why:** seamless — the customer's setup stays the one share (D-45/D-46), now as Editor for the write; the creator picks the Doc and chooses its heading from the Doc's own headings (or types it), the platform reads the section, and the end user approves one card that previews exactly the before and after text, with the Edit form they already know. Scalable — the replace rides the task machinery, the lease and the reconcile every tenant already runs, one `drive` scope constant serves reads and writes, and the connector is chosen by manifest; the revision lock needs no stored marker per write (the Doc's own revision is the lock), so a retry converges without a second marker path. A heading (the alternative: a named range the creator creates in the Doc) needs no per-section setup inside Google — the creator names a heading that already exists — and a renamed or removed heading refuses in plain words rather than writing the wrong place.
- **Consequence:** replacing needs the share to allow editing: a Doc shared with the address as Viewer only is readable but the replace is refused (a 403 the error table reads as lost access), and the task tells the requester it could not replace — the settings docs say Editor is needed for the write. The replacement lands as the tenant's agent account, never the asker. The section is located from the read revision's paragraph indices, frozen into the draft: a Doc that moved between the read and the write refuses (the revision lock), so the indices are never applied to a changed body. One heading per section grant: the Doc's file ID is granted once across kinds, so a Doc is either a read grant or a section grant, not both; a section grant is granted as for reads (the Doc is indexed and citable, unlike a template). A tenant's no-approval policy never reaches a replace: the manifest tool is not low-risk. The shape check also runs before reconcile's look: a republish since the draft stops the look, and the task says it could not confirm and points to the Doc — never that nothing was written, since a section an earlier attempt replaced may already hold the approved text. The exactly-once residual is the revision lock's: a Doc whose revision a collaborator changed and then changed back to the read revision between attempts is not distinguished (the revision is monotonic at Google, so this does not occur in practice). Submit's two reads (metadata then body) leave a residual too: a collaborator edit between them is not distinguished — submit checks the body it read, and the draft re-reads and the write locks to the draft revision, so a later move is caught there. The plain-paragraphs bound keeps the write a literal text insert: a section with a table or image is refused rather than rewritten, and the 5,000-character before bound keeps the card able to show the whole section. Recorded with the build 2026-11-21; the heading model (replacing the named range), approval always and no watch are the maintainer's (2026-11-21); plain paragraphs only, the length bound and the picker heading step are the maintainer's (2026-11-21).
